# 需求提案（proposals）

每条需求一个目录，**目录名 = `YYYY-MM-DD-<slug>`**（日期 = 需求提出日，slug 用英文短横线）。
这里放**需求正文**：为什么做、做到什么程度、边界在哪、用户拍了哪些板、数据依据是什么。

架构方案写 `docs/DESIGN*.md`，任务拆解与验收清单写 `docs/TASKS*.md`，验收记录写 `docs/reports/`。
三者不重复：提案回答「要什么」，设计回答「怎么建」，任务回答「谁做什么、怎么算完」。

## 目录内的文件

单条需求小就一个 `README.md`；需要展开时按下面的编号拆，缺项直接跳过编号：

| 文件 | 内容 |
|---|---|
| `README.md` | 一句话需求 + 元信息表 + 文件索引 + 关联文档 |
| `00-requirement.md` | 用户原话、澄清过程、定稿后的需求陈述、不在范围内的事 |
| `01-decisions.md` | 逐条拍板的决策，每条写清结论与理由 |
| `02-rules.md` | 规则或算法细则（有规则的需求才有） |
| `03-data-baseline.md` | 数据摸底与预算测算，附可复算脚本 |
| `04-scope.md` | 改动面、验收口径、协作安排 |
| `05-open-questions.md` | 遗留问题与后续路径 |

## 写作约定

- 用户原话逐字保留，不要润色成需求文档腔；澄清与推断另起段落，标明是主会话的判断。
- 决策要写**理由**，尤其是被否掉的选项，避免后面重复讨论。
- 数字必须可复算：附脚本或命令，注明数据快照日期。
- 需求定稿后原文不改。后续变更追加「变更记录」小节或新开提案，链回旧提案。
