# 01 已拍板的决策

主会话给出四个问题 + 用户追加两条约束，全部已定。

## D1 规模档位（已确认）

起步档：**主网 + 去重后公开 https 端点数 ≥ 5**，每链最多采样 8 个端点做探测，约 190 条链。
跑稳后再考虑放宽到 ≥ 3（约 592 条）。

理由：直接上 ≥ 3 会让探针负载涨约一倍，且尾部大量链实际只有 1 个能用的端点，
晋级也过不了，白白消耗探测预算。数据见 `03-data-baseline.md`。

## D2 测试网（已确认）

自动开启集合**只收主网**。测试网保持按需 hot 激活，不做白名单。

## D3 与人工操作的优先级（已确认）

优先级：`config.chains`（配置 pinned） > 人工覆写 > 自动开启。

- 人工在控制台做过的决定，规则引擎永远不覆盖。
- 自动集合持久化在状态存储，人工覆写继续走既有 `override:chain:{id}`。

## D4 首页语义（已确认）

`pinned` / `hot` / `dormant` 是内部生命周期词，不对外暴露。公共页只显示两档：

- **available**：内部 pinned/hot 且有活跃端点；
- **unverified**：其余非 disabled 链。

公共链表**默认只列已开启的链**，其余靠搜索可见（`q` 非空或 `scope=all` 时返回全目录，
disabled 链始终不可见）。

## D5 只增不减，减法只有人工（用户追加，硬约束）

- 作用域是**链级开启状态**；端点级冷却摘除与恢复回池（硬指标 2）不受影响。
- 规则只加不删。已开启链即使端点全部失效也保持开启，只在展示上体现为不可用。
- 集合必须**持久化**：重启后重算若丢链，等于机器做了减法。状态存储不可写时**暂停晋级**，
  不允许只在内存里生效。
- 减法复用既有管理动作，不新增语义：取消开启（`unpin`）让链回到按需服务，
  禁用（`disable`）直接 403。两者都是**墓碑**，规则引擎永远跳过；重新纳入靠人工。
- 集合上限 400 条，达到后**停止新增**，绝不淘汰已开启链，由人工决定是否提高上限。

## D6 不依赖 Prometheus（用户追加，硬约束）

- 判定只用进程内探测结果，不读 `/metrics`，不依赖任何外部时序库。
- 运行状态一律通过 Admin API 与 dashboard 呈现；`metrics_enabled = false` 时功能与
  可观察性都完整。
- 只补少量**不带链标签**的全局标量指标，不新增按链的时间序列，避免基数随链数膨胀。
