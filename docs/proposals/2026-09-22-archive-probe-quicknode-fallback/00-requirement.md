# 需求正文

## 用户原话

> check下代码和架构，新增两个功能：
> 1. 探测是否是归档节点，以及时延
> 2. 最后兜底策略，我会给个别链配置一个quicknode

没有后续澄清。下面的边界是对照现有探针、候选池和转发路径之后定的，不是用户逐条确认过的。

## 定稿需求

1. 对已激活链上的每个端点（含付费兜底）探测它能否提供归档状态，并记录这次探测的时延。结论和管理面上已有的存活时延分开存放，能在链详情里看到。
2. 运维可以为个别链配置一个 QuickNode（或其他付费 HTTP RPC）URL。公共池还能正常返回时不用它。公共池失败之后再试这一个 URL 一次。成功则调用方无感知；它自己的密钥不出现在日志、指标和公共页面里。

## 不在范围内

- 不按方法把历史状态请求改路由到归档节点。探测只打标签，公共池的选择规则不变。
- 不自动发现或申请 QuickNode，一条链只接受一个兜底 URL。
- 不把归档结论写进 Redis。重启后下一轮探针重判。
- 不改 10k QPS、冷却摘除、hedge 占比这些既有硬指标的语义。
